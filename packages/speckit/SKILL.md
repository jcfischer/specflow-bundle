# SpecKit - Spec-Driven Development

**Spec-Driven Development (SDD)** inverts traditional development: specifications become executable artifacts that directly generate implementations. Based on [GitHub's spec-kit](https://github.com/github/spec-kit).

## Core Philosophy

> "Specifications don't serve code - code serves specifications."

Instead of coding first and writing docs later, start with a spec. This spec becomes the source of truth your tools and AI agents use to generate, test, and validate code.

### The Doctorow Principle

> "Code is a liability, not an asset. The capabilities code generates are valuable, but the code itself requires constant maintenance."

Every feature adds not just capability but also **maintenance burden**. SpecKit tracks this through:
- **Failure Mode Analysis** — How will this code break?
- **System Context Mapping** — What depends on this? What does this depend on?
- **Technical Debt Ledger** — Explicit tracking of liability
- **Longevity Assessment** — When should this code be deleted?
- **Doctorow Gate** — Post-implementation verification that code "fails well"

## Four-Phase Workflow

```
SPECIFY -> PLAN -> TASKS -> IMPLEMENT
   |         |        |         |
 What/Why   How    Work Items  Code
```

**Gated phases**: Do NOT advance until current phase is validated.

### Phase 1: Specify (`/speckit.specify`)

**Begins with Interview**: Uses the Interview skill to conduct structured requirements elicitation via AskUserQuestion before writing the spec.

Interview covers 8 phases:
1. Problem & Pain - What we're really solving
2. Users & Context - Who benefits and how
3. Technical Context - What exists today
4. Constraints & Tradeoffs - What matters most
5. User Experience - How it should feel
6. Edge Cases - What could go wrong
7. Success Criteria - How we know it's done
8. Scope & Future - What's in and out

**pai-deps Integration**: If modifying an existing tool, run:
```bash
pai-deps speckit context <tool> --json
```
This auto-populates the System Context section with real dependency data.

After interview, synthesizes answers into spec containing:
- User journeys and scenarios
- Functional requirements (with failure behavior)
- Success criteria
- Key entities
- Assumptions (with invalidation conditions)
- **System Context** — Auto-generated from pai-deps:
  ```markdown
  ## System Context
  <!-- Generated by: pai-deps speckit context <tool> -->
  - **Upstream**: email (cli, 95%), resona (library, 95%)
  - **Downstream**: daily-briefing, meeting-intelligence
  - **Compound Reliability**: 90.2%
  - **Blast Radius**: 3 tools affected
  - **Warnings**: Chain reliability below 80%
  ```

**Output**: `specs/<feature>/spec.md`

### Phase 2: Plan (`/speckit.plan`)

Convert specification into technical design:
- Architecture decisions with rationale
- Data models and schemas
- API contracts
- Technology choices
- Constitutional compliance check
- **Failure Mode Analysis** — How code fails, assumption fragility, blast radius
- **Longevity Assessment** — Maintainability, evolution vectors, deletion criteria
- **Debt score calculation** — Explicit liability tracking

**pai-deps Integration**: Run these commands to inform the plan:
```bash
# Get failure modes for each dependency
pai-deps speckit failures <tool> --json

# If modifying existing tool, check blast radius first
pai-deps blast-radius <tool> --json

# Check what else might need updating
pai-deps affected <tool> --json
```

Include auto-generated sections in plan.md:
```markdown
## Failure Mode Analysis
<!-- Generated by: pai-deps speckit failures <tool> -->
| Dependency | Mode | Detection | Recovery | Severity |
|------------|------|-----------|----------|----------|
| email | CLI unavailable | Non-zero exit code | Skip, continue partial | MEDIUM |
| resona | Library exception | Catch block triggered | Log, degrade gracefully | CRITICAL |

## Impact Assessment
<!-- Generated by: pai-deps blast-radius <tool> -->
- **Risk Level**: MEDIUM (score: 34.2)
- **Direct dependents**: 3 tools
- **Transitive dependents**: 5 tools
- **Rollback strategy**: Test MCP tools first, verify direct dependents
```

**Output**: `specs/<feature>/plan.md`, `data-model.md`, `contracts/`

### Phase 3: Tasks (`/speckit.tasks`)

Break plan into reviewable units:
- Task IDs (T-1.1, T-1.2, etc.)
- Dependencies marked
- Parallel tasks marked `[P]`
- Test requirements marked `[T]`

**Output**: `specs/<feature>/tasks.md`

### Phase 4: Implement (`/speckit.implement`)

Execute tasks with TDD enforcement:
- Write failing test first (RED)
- Minimal implementation (GREEN)
- Refactor (BLUE)
- Run full test suite
- Proceed to next task

**pai-deps Integration**: After implementation, register and verify:
```bash
# Register the tool (creates/updates pai-manifest.yaml)
pai-deps init <path>
pai-deps register <path>

# Verify contracts are valid
pai-deps verify <tool>

# Check chain reliability hasn't degraded
pai-deps chain-reliability <tool>
```

**Doctorow Gate (Post-Implementation Verification):**
- [ ] Failure test — Intentionally break external dep → graceful failure?
- [ ] Assumption test — Behavior when key assumption wrong?
- [ ] Rollback test — Can disable without breaking other features?
- [ ] Debt recorded — Entry added to debt-ledger.md?
- [ ] **pai-deps registered** — `pai-deps show <tool>` returns tool info
- [ ] **Contracts verified** — `pai-deps verify <tool>` passes
- [ ] **Reliability threshold** — `pai-deps chain-reliability <tool>` > 80%

```bash
# Doctorow Gate verification script
pai-deps show <tool> || echo "FAIL: Tool not registered"
pai-deps verify <tool> || echo "FAIL: Contracts invalid"
pai-deps chain-reliability <tool> --min 0.8 || echo "WARN: Below 80% reliability"
```

**Triggers existing TDD workflow from TESTING.md override.**

## Spec Numbering System

All specs are assigned a unique 3-digit ID from the central registry.

### Registry Location
```
~/.claude/skills/SpecKit/spec-registry.json
```

### ID Format
- **Format**: 3-digit zero-padded number (001, 002, ... 073)
- **Tracking**: `lastId` field tracks highest assigned ID
- **Assignment**: Increment `lastId` and use for new spec

### Directory Naming Convention
```
<project>/.specify/specs/<ID>-<feature-name>/
```

**Examples**:
- `healthcare-report-automation/.specify/specs/051-document-storage-hierarchy/`
- `supertag-cli/.specify/specs/073-error-context/`
- `email/.specify/specs/001-imap-drafts/`

### Registry Entry Structure
```json
{
  "id": "051",
  "feature": "document-storage-hierarchy",
  "skill": "healthcare-report-automation",
  "path": "healthcare-report-automation/.specify/specs/051-document-storage-hierarchy",
  "status": "draft",
  "created": "2025-12-30"
}
```

### Status Values
| Status | Meaning |
|--------|---------|
| `draft` | Spec in progress, not yet approved |
| `completed` | Implementation finished |
| `abandoned` | Spec cancelled or superseded |

### When Creating a New Spec

1. Read `spec-registry.json` to get current `lastId`
2. Increment to get new ID (e.g., 73 → 74 → "074")
3. Create directory: `<project>/.specify/specs/074-<feature-name>/`
4. Add entry to registry with new ID
5. Update `lastId` in registry

## Directory Structure

For each feature:

```
.specify/
├── memory/
│   └── constitution.md       # Project-specific principles
├── debt-ledger.md            # Technical debt tracking (project-wide)
└── specs/
    └── <ID>-<feature-name>/
        ├── spec.md           # Requirements (Phase 1)
        ├── plan.md           # Technical design (Phase 2)
        ├── research.md       # Technology decisions
        ├── data-model.md     # Schemas
        ├── contracts/        # API definitions
        └── tasks.md          # Implementation steps (Phase 3)
```

## Constitutional Inheritance

```
CORE/CONSTITUTION.md (Master - PAI principles)
       |
       v (inherits)
.specify/memory/constitution.md (Project-specific)
```

Project constitutions can ADD constraints but cannot REMOVE PAI principles.

## Integration with PAI

### TDD Enforcement

Phase 4 (Implement) MUST follow TDD workflow:
1. Write failing test
2. Verify test fails
3. Write minimal implementation
4. Verify test passes
5. Run ENTIRE test suite
6. Refactor if needed

### CLI-First

All generated code follows PAI's CLI-First Architecture:
- Library first, then CLI wrapper
- Deterministic over probabilistic
- Code before prompts

### History Integration

Completed specs archived to `${PAI_DIR}/history/specs/` for future reference.

### pai-deps Integration

SpecKit integrates with `pai-deps` for dependency-aware development:

| Phase | Command | Purpose |
|-------|---------|---------|
| SPECIFY | `pai-deps speckit context <tool> --json` | Auto-populate system context |
| PLAN | `pai-deps speckit failures <tool> --json` | Generate failure mode analysis |
| PLAN | `pai-deps blast-radius <tool> --json` | Assess impact before changes |
| PLAN | `pai-deps affected <tool> --json` | Identify what else needs updating |
| IMPLEMENT | `pai-deps init <path>` | Generate pai-manifest.yaml |
| IMPLEMENT | `pai-deps register <path>` | Register tool in dependency graph |
| IMPLEMENT | `pai-deps verify <tool>` | Verify CLI/MCP contracts |
| DOCTOROW GATE | `pai-deps chain-reliability <tool>` | Verify > 80% compound reliability |

**When to use pai-deps:**
- **New tool**: Run `pai-deps init` after implementation to generate manifest
- **Modifying existing tool**: Run `blast-radius` and `affected` BEFORE planning
- **Adding dependencies**: Update pai-manifest.yaml and re-register
- **Changing contracts**: Run `pai-deps verify` to catch breaking changes

**Reliability thresholds:**
- **> 90%**: Healthy chain, proceed normally
- **80-90%**: Acceptable, consider adding redundancy
- **< 80%**: WARNING - add error boundaries, consider simplifying chain

## Example Usage

```bash
# User: "I want to add RSS feed discovery to ragent"

/speckit.specify RSS feed auto-discovery that finds related feeds from existing sources

# Creates: .specify/specs/rss-discovery/spec.md
# User reviews and approves spec

/speckit.plan TypeScript, Bun, SQLite, existing ragent patterns

# Creates: plan.md, data-model.md, contracts/
# User reviews architecture decisions

/speckit.tasks

# Creates: tasks.md with T-1.1, T-1.2, etc.
# Shows dependencies and parallel opportunities

/speckit.implement

# Executes tasks with TDD:
# - T-1.1: Create FeedDiscovery schema [T]
# - T-1.2: Add discovery CLI command [T]
# - etc.
```

## When NOT to Use

- Simple bug fixes (just fix it)
- Single-line changes
- Exploratory spikes (prototype first, spec later)
- Documentation-only changes
